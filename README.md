# Исправления багов 1–3

Патч для последней присланной версии бота с одним экземпляром `Bot`.

## Установка

1. Остановить бот.
2. В Supabase SQL Editor выполнить `fix_1_3.sql`. Он рассчитан на БД, в которой **уже выполнена предыдущая миграция** с `queue_adjustments`, `events` и RPC. Старую миграцию повторно запускать не нужно. Этот дополнительный патч не удаляет `priority` или другие старые данные.
3. Заменить в существующем проекте:
   - `main.py`;
   - `private/handlers/assign_lead.py`;
   - `private/handlers/priv_handler.py`.
4. Добавить `private/handlers/pending_leads.py`.
5. Запустить бот обычным способом. `database.py`, `events.py`, групповой обработчик и существующие файлы пакетов остаются в проекте. Для RPC обработчика ожидающих лидов нужен серверный ключ Supabase с ролью `service_role`.

Бот начнёт подбирать уже существующие неназначенные лиды после запуска. Новые зависимости Python не добавлены.

## Поведение

- Если у всех ONLINE-получателей есть пропуски, алгоритм расходует их по одному на соответствующем ходе и продолжает следующие круги для **того же лида**. При конечном количестве пропусков и наличии получателя лид будет назначен.
- Если получателей нет, лид остаётся в `leads` без оформителя. Фоновый обработчик проверяет ожидающие лиды каждые 3 секунды, партиями до 20. После перехода ONLINE или перезапуска он назначает их автоматически.
- Ожидающие лиды обрабатываются по `created_at, id`. Новый лид не обгоняет старые ожидающие лиды своей категории. Категория без ONLINE-получателей не блокирует остальные категории.
- Мусор никогда не подбирается обработчиком ожидания.
- У очереди появился `current_round`, у участника — `eligible_from_round`. OFFLINE → ONLINE подключает сотрудника к следующему кругу **каждой** категории. Текущие ONLINE-участники при установке патча сохраняют свои места.
- Пример: последний получатель A, очередь A/B/C; вернулся B. В текущем круге получит C; затем новый круг начинается с A, далее B. При возмещениях действует их приоритет, но они тоже не обходят ограничение на круг подключения.
- Если все были OFFLINE, после появления ONLINE-получателя планировщик сразу переходит к кругу его допуска. Для этого не нужны пустые заявки или ручное продвижение очереди.
- Повторное нажатие ONLINE не откладывает подключение ещё на круг. Сам OFFLINE не создаёт пропусков и возмещений.
- `/queues` вызывает тот же SQL-планировщик; просмотр не расходует корректировки и не продвигает очередь.

## Доставка ожидающих лидов

Назначение и запись задания на личное уведомление сохраняются в одной транзакции. Ошибка Telegram повторяет **уведомление**, а не распределение. Записи находятся в `pending_lead_notices`; для диагностики есть `attempts`, `last_error`, `next_attempt_at`, `sent_at`.

После перезапуска незавершённое задание доступно повторно по истечении аренды до 2 минут. Интервал повторных попыток постепенно увеличивается до нескольких минут. Сообщение идёт только назначенному получателю, даже если он позже стал OFFLINE: назначение уже состоялось.

Доставка имеет семантику «как минимум один раз»: если Telegram принял сообщение, но процесс упал до записи `sent_at`, возможно повторное уведомление с тем же ID лида. Повторного назначения или повторного расходования очереди не происходит.

Этот обработчик доставляет только отложенные назначения. Обычная немедленная отправка `/send` остаётся в существующем обработчике и не дублируется фоновым процессом.

## Проверка

В среде подготовки выполнены **11 Python-тестов** обработчика доставки и RPC-просмотра, а также проверка синтаксиса Python и оболочки. Они не обращаются к Telegram или рабочей БД.

```bash
python -m unittest discover -s tests -v
```

SQL-регрессии подготовлены, но **не выполнены в среде подготовки: PostgreSQL недоступен**. Для реальной проверки используйте пустую одноразовую PostgreSQL-базу:

```bash
TEST_DATABASE_URL='postgresql://user:password@localhost/test_bot' bash tests/run_sql_tests.sh
```

Скрипт создаёт тестовую базовую схему, применяет патч дважды для проверки повторного запуска и проверяет обычную очередь, всеобщие и множественные пропуски, одинокого ONLINE-получателя, границы кругов, возмещения, дубли, ожидание, приоритет старых заявок, изоляцию категорий, мусор, аренду уведомлений, нулевую позицию и откат транзакции. Он откажется создавать фикстуры в базе с существующими `leads` или `team_members`. Не запускайте тестовые фикстуры на рабочей БД.

Тестовая базовая схема отражает использованные в присланном коде поля; она не подтверждает совместимость с неизвестными ограничениями и триггерами вашего Supabase. Миграция не выполнялась в рабочем Supabase.

Патч относится к багам 1–3. Остальные замечания предыдущего аудита, включая `/cancel`, старые кнопки `/change`, полноту журнала и логирование ключа в `database.py`, в этот патч не входят.
